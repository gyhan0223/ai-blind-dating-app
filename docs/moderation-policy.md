# 신고·차단 운영 정책 (#15 · #16)

코드가 구현한 기준을 적는다. 법률 검토(#12) 전이므로 "운영 기본값" 이며, 사유·조치 기준은 운영하면서 이 문서와 함께 바꾼다.
**자동 제재는 없다.** 모든 정지·차단은 운영자가 관리자 웹에서 신고와 신호를 보고 결정하고, 감사 기록(`moderation_actions`)이 남는다.

## 1. 사용자가 할 수 있는 것

| 행동 | 위치 | 효과 |
|---|---|---|
| 신고 | 채팅 헤더 깃발 아이콘(1탭) · 채팅 메뉴 · 만남 화면 · 대화 목록 길게 누르기 없음 | `reports` 행. 상대에게 알려지지 않는다 |
| 차단 | 신고 화면의 "신고와 함께 차단" / "신고 없이 차단만" | 즉시 매치 종료(`blocks` 트리거), 메시지·의향 교환 차단, 서로 재추천 제외(#43). 대화 이력은 보존 |
| 긴급 표시 | 신고 화면 "긴급해요" | `severity=urgent` — 위협·스토킹·성적 발언·성희롱·금전 요구 사유에서만 선택 가능. 위협·스토킹·미성년 의심은 자동 urgent |

신고 사유: 불쾌한 대화 · 성적인 발언 · 성희롱/괴롭힘 · 위협 · 스토킹 · 금전 요구/사기 · 개인정보(연락처·신상) 요구 · 사칭 · 허위 정보 · 미성년 의심 · 스팸 · 기타.

## 2. 사유별 기본 조치 기준 (운영자 판단의 출발점)

| 사유 | 1회 | 반복(30일 2회 이상) | 즉시 영구 차단 |
|---|---|---|---|
| 불쾌한 대화 / 허위 정보 / 스팸 | 경고 | 7일 정지 | 3회 이상 |
| 성적인 발언 / 성희롱 | 경고 또는 7일 정지 | 30일 정지 | 명백한 성희롱·미성년 대상 |
| 개인정보 요구 / 외부 메신저 유도 | 경고 (초반 대화 신호와 함께 확인) | 7일 정지 | 금전 요구와 결합 |
| 금전 요구 / 사기 | 7일 정지 + 대화 확인 | 영구 차단 | 계좌·송금 요구가 확인되면 즉시 |
| 위협 / 스토킹 | **긴급** — 당일 확인, 확인 즉시 정지 | 영구 차단 | 위해 가능성이 있으면 즉시 |
| 사칭 | 정지 + 본인확인 재요청 | 영구 차단 | 신분 도용 확인 시 |
| 미성년 의심 | **긴급** — 즉시 정지, 본인확인 기록 확인 | — | 미성년 확인 시 (identity banned) |

- 경고는 상태를 바꾸지 않고 감사 기록만 남긴다 (사용자에게 별도 통지 기능은 없다 — 앱 내 통지는 후속).
- 기간 정지는 `suspended_until` 로 저장되고 `moderation_lift_expired_suspensions()`(cron 1시간)가 자동 해제하며 해제도 감사 기록으로 남는다.
- 영구 차단(`banned`)은 `user_identities.banned` 에 동기화되어 전화번호를 바꿔 재가입해도 막힌다 (0009). 활성 매치는 닫히고 기기 토큰은 삭제된다.
- 신고자 보호: 신고 내용·신고 여부는 상대에게 보이지 않는다. 피신고자에게 신고자 정보를 알리지 않는다.

## 3. 긴급 신고 우선 처리

- `severity=urgent` 는 관리자 신고 목록 맨 위에 빨간 배지로 표시된다. 목표: 24시간 안 1차 확인.
- 확인 순서: 신고 상세 → 피신고자 요약(30일 피신고 수·조치 이력·위험 신호 수) → 필요 시 대화 확인(service role, 신고된 매치 한정) → 조치.
- 위해 가능성이 있으면 확인 전이라도 임시 정지(`suspend`, 사유 "긴급 확인 중")를 먼저 건다.

## 4. 반복 패턴

`moderation_user_summary` 뷰(service role): 사용자별 30일 피신고 수 · 30일 신고 수 · 누적 제재 수 · 30일 위험 신호 수.
관리자 신고 목록의 피신고자 옆에 표시된다. 신고를 반복하는 신고자(30일 5회 이상)도 확인 대상이다 — 신고가 자동으로 상대 제재로 이어지지 않는다.

## 5. 채팅 안전 (#16)

| 장치 | 규칙 | 결과 |
|---|---|---|
| rate limit | 대화당 60초 20건 · 사용자당 1시간 200건 | `rate_limited` — 앱은 "잠시 후 다시 보내 주세요" |
| 반복 본문 | 같은 대화에 같은 본문 5분 안 3회 | 4번째부터 `repeated_content` |
| 위험 패턴 신호 | 휴대전화 번호 · 카톡/라인/텔레그램/인스타 아이디 요구 · 계좌/송금/투자/대출 · 링크 · 좁은 욕설 목록. 대화 초반(10건 이하)의 연락처 요구는 `early_contact_request` 추가 | `moderation_signals` 에 flags 만 기록 (원문 없음). **자동 제재·전송 차단 없음** |

- 오탐 기준 테스트(`moderation_tests.sql`): "주말에 카페 갈래요?", "2010년에…", "라인 잘 잡힌…" 같은 정상 문장은 신호가 없어야 한다. 규칙을 넓힐 때 이 케이스를 먼저 통과시킨다.
- 신호는 신고 검토 시 참고 자료다. 신호만으로 사용자에게 경고를 보내거나 메시지를 막지 않는다 (정상 대화 보호). 신고가 들어온 사용자의 최근 신호가 많으면 조치 기준을 한 단계 올려 볼 수 있다.
- 연락처 교환 자체를 금지하지 않는다 — 상호 만남 의향이 확인된 뒤 번호를 주고받는 것은 정상 흐름이다. 초반(10건 이하)의 요구만 표시한다.

## 6. 관리자 워크플로우 (`apps/admin/app/reports`)

`pending` → (확인 중 `reviewing`) → `actioned`(경고/정지/차단) 또는 `dismissed`(기각). 과거 `resolved` 는 그대로 표시.
각 조치는 `admin_moderate_user(user, action, reason, report_id, actor, days)` RPC 로만 실행되며 `moderation_actions` 에 남는다.
사용자 목록의 정지/해제도 같은 RPC 를 쓴다. DB 를 직접 update 해 상태를 바꾸지 않는다 (감사 누락 방지).

## 7. 남은 것

- 사용자에게 경고·정지 사유를 앱 안에서 보여주는 화면 (지금은 정지 화면에 고정 문구).
- 신고 시 첨부(스크린샷) — MVP 는 텍스트 사유만. 신고된 매치의 대화는 서버에 남아 있어 운영자가 확인할 수 있다.
- 법률 검토(#12) 뒤 사유·보관 기간 확정.
